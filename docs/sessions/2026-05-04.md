## Production state surprises

The session's largest finding was that the previous wrap-up's framing of
priorities, while well-intentioned, didn't match the actual bug landscape.
Specifically:

**The wrap-up said `wiring.go:259 :51820` was a real migration blocker.**
Investigation showed:

- The hardcode in question is on line 237 (DDNS updater), not 259 (which is
  in a comment block). Plus two more hardcodes on lines 209 (UPnP) and 250
  (UDPBridge for vps_relay only). Three total.
- The DDNS code path is broken at the *identity* layer, not the port layer.
  `data/node_id` reads `86925361-475d-4a85-8f62-82561c442875`. Supabase has
  no row with that ID. The DDNS updater PATCHes `/rest/v1/nodes?id=eq.86925361...`
  every 5 minutes — and has for 12 days — and every PATCH silently no-ops
  because PostgREST returns 200 with an empty body when zero rows match.
- The actual canonical row is `cf238a2a-e060-4595-8a43-b030b42da88b`, the
  one children's `assigned_node_id` points at, the one heartbeat keeps fresh.
- So the `:51820` hardcode is dormant cosmetic, not a migration blocker.

**The bug we actually found:** `nodes.wireguard_port` had been frozen at
`51820` since enrollment on 2026-04-22. The Supabase function
`get_child_tunnel_config(p_device_id)` reads this column and returns
`primary_endpoint=209.38.30.90:51820` — which is wrong, because the live
WireGuard socket has been on `:443` since the LTE fix landed on 2026-04-28.
Currently-connected children were holding cached configs from before the
freeze, but any device hitting the "3 consecutive failures → refresh tunnel
config" code path would receive `:51820` and configure their endpoint to a
port with no listener (and blocked on most LTE networks).

**Why the bug self-resolved:** The heartbeat payload includes a
`tunnel.HealthSnapshot` with `ListenPort` read from the live `wg show`. The
edge function at `/functions/v1/node-heartbeat` apparently extracts that and
writes it to `nodes.wireguard_port`. Recent code (probably in `1390c5e4` or
`a7a9c80` — TBD which) made the edge function actually use this field. The
first heartbeat tick after that code went live flipped the row from `51820`
to `443`. Our PATCH 80 seconds later was redundant.

The Go code never names `wireguard_port` directly — `grep -n wireguard_port`
on `internal/controlsync/heartbeat.go` returns empty. The column→Go mapping
happens edge-function-side. Worth knowing for future debugging.

## What we didn't touch (carried forward)

**Identity reconciliation.** `data/node_id` (`86925361...`) does not match the
canonical Supabase row (`cf238a2a...`). The `86925361` ID exists nowhere in
Supabase. controlsync (heartbeat, bundle, commands, enforcement, tunnel_stats)
hits the right row anyway because it goes through edge functions that take
`node_id` as a query parameter and apparently map it server-side. The DDNS
updater bypasses the edge function and hits REST directly with the wrong ID,
silently no-op'ing every cycle. **This is a sharp edge.** Anything new that
writes to `nodes` directly via REST will hit the same trap. Real bug, low
immediate impact, real landmine.

**`wiring.go` `:51820` hardcodes (3 sites).** Lines 209 (UPnP), 237 (DDNS),
250 (UDPBridge for `vps_relay`). All cosmetic per investigation above. Safe
to fix as code hygiene; not a migration blocker.

**`99-lte-fix.conf` shellrace.** Live socket port (443) is set by a systemd
`ExecStartPost` shell loop polling `wg0` for up to 30 seconds and running
`wg set wg0 listen-port 443`. Should be folded into Go code (set listen port
at WG-bring-up, not after). Real architectural smell — but less dangerous
than it looked, because the heartbeat-port-write path uses the live `wg show`
port as source of truth, so once the shellrace wins the heartbeat eventually
publishes the correct value to Supabase.

## Learnings worth recording

1. **The previous wrap-up's priorities described real concerns, but
   mid-session investigation showed the cause was different from what the
   wrap-up assumed.** Specifically: "wiring.go line 259 :51820 hardcode =
   real migration blocker" mapped to a wrong line number AND a code path
   that's broken at the identity layer rather than the port layer. Future
   wrap-ups: when calling something a "blocker," verify the code path is
   actually live before downstream sessions inherit the framing.

2. **There are two parallel Supabase write paths from this router with
   different identity sources, and they have different reliability
   semantics.** controlsync goes through edge functions which appear to map
   the wrong `node_id` to the right row server-side. The DDNS updater uses
   raw REST PATCH which has no such mapping and silently no-ops. Anything
   new that writes to `nodes` directly via REST will hit the same trap.

3. **The heartbeat-edge-function writes `wireguard_port` from the live
   `wg show` port.** This is a subtle indirection: the Go code doesn't
   reference `wireguard_port` anywhere, but the field travels through the
   heartbeat health snapshot and gets unpacked server-side. Source of truth
   for the published port is the live socket, not config. Worth knowing
   for future debugging.

4. **Comment-vs-code drift is a recurring problem in this codebase.** The
   `nrdsync.go:358-363` "Uses anon auth" comment contradicts the actual
   `authServiceRole` the code uses. Same general failure mode caused us to
   misread the `:51820` hardcode as live. Worth flagging anytime a comment
   makes a claim about behavior — verify the code agrees.

5. **The `service.go:95-104` "NRD ingest disabled 2026-05-01" comment was
   load-bearing context that the prior wrap-up didn't capture.** Without
   it, the orphaned-NRD-files question would have looked like "should we
   delete dead code?" instead of "should we commit dormant code with a
   re-enable plan?" Future wrap-ups: explicitly call out disabled-but-not-
   deleted code paths.

6. **Production state can change between investigation and intervention.**
   We investigated the `wireguard_port` bug at ~13:18 (saw `:51820` in
   function output), planned a hotfix, ran it at `13:25`, and discovered
   the bug had self-resolved at `13:24:16` — between the investigation
   and the fix. The next time something looks broken-then-fixed, check the
   timestamps before claiming credit.

7. **`grep` with restrictive `--include` and `grep -v` chains can hide
   important references.** Mid-session, an early grep for "nrd_blocklist
   references" returned empty because of cumulative filters; a re-grep
   without the filters showed the file was actively referenced from
   `wiring.go` and `resolver.go`. Always sanity-check empty grep results
   before drawing conclusions from them.

8. **The chat-display pipe between this VPS terminal and the chat client
   auto-links any string matching `<dashes-and-digits>.md` and similar
   patterns, transforming both directions of the conversation. Filenames
   matching that pattern cannot survive a round-trip through copy-paste.
   Workaround: use filenames that don't match the trigger, then rename via
   programmatic methods (Python `os.rename`) once written.**
